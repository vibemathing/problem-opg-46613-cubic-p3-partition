# 架构设计原则

## 目标终态

Vibe Mathing 的架构必须让非可信候选、受信验证、事实账本和派生视图保持单向依赖：

```text
ProblemContract
  -> Attempt / candidate Result
  -> registered verifier + immutable receipt
  -> Result evidence ledger
  -> Solution View / ResearchBundle
```

任何模型、CAS、solver 或 proof assistant 都只是该链上的有界生成器或验证器，不能成为隐藏的第二真相源。

## 原则

1. 单一真相：Problem、Attempt、Result 分别只有一个 owner；ResearchBundle、Solution View 和成熟度分数必须纯派生。
2. 信任分层：generator 与 verifier 的身份、能力和 trust domain 由 registry 派生，禁止调用者自报独立或 PASS。
3. 依赖单向：技能和 adapter 消费契约，证据层消费 artifact；派生视图不得反向改写问题或历史证据。
4. 能力有界：每个工具必须声明支持范围、版本、预算、失败语义和升级触发条件；有限 solver 不能冒充一般证明。
5. 失败闭合：未知 provider、unsupported theory、版本漂移、超时、矛盾闭合和证据失效必须显式非零或 `undetermined`。
6. 存在性优先：优先平台、标准库、项目原生能力和成熟依赖；没有真实消费者、owner 与验证命令的对象不创建。
7. 文档随事实：工具链、模块边界、验证入口或证据语义变化时，同步 owner README/AGENTS、Toolchain Model、module context、ADR/Gate 或明确豁免。

## 架构门槛

- 新 adapter 必须有固定 fixture、正负例和可重算 artifact/receipt。
- 新外部 provider 必须有非敏感 registry、timeout、有限重试、脱敏审计摘要和显式 live 模式。
- 新 proof/solver backend 必须与 statement-faithfulness 分开裁决。
- 新缓存、数据库、队列或并发层必须先有 profile/规模证据，并给出一致性与回滚契约。
- 所有“100%”必须声明 scope、excluded 项和从真实退出码派生的 capability matrix。

## 反模式

- 用模型自评、自然语言 review 或硬编码分数替代 verifier。
- 把动态网页、API 在线状态或无凭据环境写成离线 CI 的稳定事实。
- 为尚不存在的第二 backend 创建 plugin/factory/registry 抽象。
- 让 task 状态、tmux pane 状态或 Goal 文本覆盖数学事实状态。
- 因旧目录或迁移麻烦长期保留双轨 owner、兼容壳或错误概念。
